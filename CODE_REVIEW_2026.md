## CRITICAL (1)

### 1. Monthly non-day-normalized HDD/CDD models inject interval_start/interval_end POSIXct columns as regressors

- **File:** `R/model_with_HDD_CDD.R`  
- **Lines:** 127-133, 161-167, 197-203  
- **Severity:** critical · **Category:** numerical/statistical

**Description:** In model_with_HDD_CDD.R, the Monthly + day_normalized==FALSE branches (the DEFAULT path, since assign_model_inputs sets day_normalized=FALSE) build the regression frame by dropping only named columns and then any "_perday" columns. They fail to drop the POSIXct columns interval_start and interval_end that aggregate.R (lines 446-447) adds to the monthly dataframe. As a result lm(eload ~ ., data=df) silently includes interval_start and interval_end as numeric regression predictors alongside HDD/CDD. With real varying month lengths both columns receive nonzero coefficients (only collinear/aliased if all months are equal length), corrupting the intercept and HDD/CDD slopes and consuming extra degrees of freedom. calculate_model_predictions then extrapolates this spurious time trend onto the prediction period's interval values, producing wrong baseline predictions and wrong ASHRAE G14 savings/uncertainty with no error or warning. Affects HDD-CDD, HDD, and CDD regression types at the Monthly/non-normalized branch. The day_normalized==TRUE branches are unaffected because their second select keeps only "_perday" columns. No tests exercise model_with_HDD_CDD, so golden-file tests cannot catch this; this is a regression introduced when interval_start/interval_end were added to aggregate output without updating the model select logic.

**Evidence:**
```r
df <- training_data %>% dplyr::select(-c("time", "temp", "HDD_perday", "CDD_perday", "days"))
        df <- df %>% dplyr::select(! dplyr::contains("_perday"))
        linregress <- stats::lm(eload ~ ., data = df)
```

**Fix direction:** Explicitly drop interval_start and interval_end (and any other non-predictor columns) in the non-day-normalized monthly branches, or whitelist the exact predictor columns (eload, HDD, CDD) instead of using a negative/contains-based select. Mirror the day_normalized approach of selecting only the intended columns, and mirror model_with_CP.R lines 52/61 which already drop these columns.

### 2. observation_count hardcoded to 12 makes normalized-savings alpha a constant independent of data length

- **File:** `R/normalized_savings_and_uncertainty.R`  
- **Lines:** 90-101  
- **Severity:** high · **Category:** numerical/statistical

**Description:** In calculate_norm_savings_and_uncertainty (R/normalized_savings_and_uncertainty.R, lines 90-101), the ASHRAE G14 small-sample correction factor observation_count is hardcoded to 12 for both Daily and Monthly intervals, making alpha a constant independent of the actual training period length. The sibling calculate_savings_and_uncertainty derives observation_count from the data (day-count/~30.5 for Daily, row count for Monthly). As a result, normalized savings uncertainty is computed with the wrong alpha for any period other than ~12 months (e.g. for a 2-year daily baseline alpha is ~23% too high), silently biasing reported uncertainty that drives ASHRAE G14 compliance reporting. **Evidence:**
```r

 alpha <- ( - 0.00024 * (observation_count ^ 2) + (0.03535 * (observation_count) + 1.00286))
} else if (... == "Monthly") {
 observation_count <- 12
 alpha <- (- 0.00022 * (observation_count ^ 2)) + (0.03306 * (observation_count)) + 0.94054
}
```

**Fix direction:** Derive observation_count from the training data as in calculate_savings_and_uncertainty.R: for Daily use length(training_data$time)/mean days-per-month (~30.5), for Monthly use length(training_data$time). Apply consistently to baseline and performance counts.

### 3. Normalized non-Monthly uncertainty uses autocorrelation-corrected DOF with no guards, yielding silent NaN

- **File:** `R/normalized_savings_and_uncertainty.R`  
- **Lines:** 131-137, 152-153, 160-165  
- **Severity:** high · **Category:** numerical/statistical

**Description:** In calculate_norm_savings_and_uncertainty, the non-Monthly uncertainty branch (lines 160-165) unconditionally uses autocorrelation-corrected degrees of freedom: dof_dash = n_dash - #Parameters with n_dash = n*(1-rho)/(1+rho). When residual autocorrelation rho is high (common for Hourly/15-min load data, typically 0.8-0.97) and/or the period is short or the model has many parameters (TOWT), dof_dash can become <= 0, in which case stats::qt(df = dof_dash) returns NaN and sqrt(MSE_dash) with negative MSE_dash returns NaN. The function then silently returns NaN normalized-savings uncertainty with no error or warning. The sibling calculate_savings_and_uncertainty.R guards exactly this with suppressWarnings around qt, an explicit `if (deg_of_freedom_dash < 0) stop(...)`, and — per ASHRAE Guideline 14 pg 91 — only applies the dash quantities when rho >= 0.5 (otherwise using uncorrected df). The normalized function has none of these three protections and diverges from the ASHRAE rule the package applies in the sibling.

**Evidence:**
```r
baseline_dof_dash <- n_dash - baseline_stats$`#Parameters`
...
baseline_t_stat_dash <- stats::qt(..., df = baseline_dof_dash)
...
baseline_normalized_uncertainty <- (baseline_t_stat_dash * alpha)*(...) * sqrt(baseline_MSE_dash * (1+(2/n_dash)) * g)
```

**Fix direction:** Add a check that baseline_dof_dash and performance_dof_dash are > 0 before using them (stop with a clear message as in the sibling), wrap qt() in suppressWarnings, and mirror the sibling's `rho < 0.5` decision to fall back to non-dash DOF when autocorrelation is low. Surface rho from calculate_independent_points so it can be tested.

### 5. mean(30,31) returns 30 not 30.5, corrupting monthly end-alignment correction

- **File:** `R/align_data.R`  
- **Lines:** 30  
- **Severity:** high · **Category:** correctness

**Description:** In R/align_data.R line 30, the monthly end-alignment offset is computed as 60*60*24*mean(30,31). mean(30,31) does not average 30 and 31; the 31 binds to mean()'s `trim` argument, so the call silently returns 30 (no warning). The correction is therefore a flat 30-day shift (2592000 s) rather than the intended ~30.5 days. After subtracting 30 days and applying lubridate::floor_date(..., "month"), monthly timestamps are mislabeled: e.g. a first-of-month timestamp 2021-03-01 shifts to 2021-01-30 and floors to January, dropping February and duplicating January. Since align_data() is an exported precursor to create_dataframe(), this silently corrupts month labels for monthly M&V data. Even the intended 30.5-day value would remain fragile due to variable month lengths, so a correct fix should compute the per-timestamp month offset robustly rather than subtract a fixed duration. (Note: align_data is exported but has no internal callers, so the corruption only reaches users who call it directly.)

**Evidence:**
```r
correction <- 60*60*24*mean(30,31)
corrected_index <- lubridate::floor_date(zoo::index(data_xts) - correction, "month")
```

**Fix direction:** Do not use a fixed-day offset for months. For each end-of-period timestamp, compute the correct prior-period start robustly, e.g. lubridate::floor_date(zoo::index(data_xts) - lubridate::days(1), "month") so any timestamp landing on/after the 1st maps to the correct month regardless of month length. At minimum replace mean(30,31) with 30.5 if a flat offset is kept.

### 9. Infinite loop / runaway when knot count reaches 1 (guard checked after decrement)
